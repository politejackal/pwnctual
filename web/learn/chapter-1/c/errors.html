Now here is a secret: your code will almost never work the first time. Not yours, not mine, not anybody's. Everybody gets errors all the time, even programmers with 20 years of experience. The difference is that they know how to read them. So let's learn how!

Reading a compiler error

Say we forgot a semicolon:

#include <stdio.h>

int main() {
    printf("Hello, World!")
    return 0;
}

When we run make hello, the compiler refuses and says:

hello.c:4:28: error: expected ';' before 'return'

This looks scary, but it's actually super helpful. Let's break it down:

  • hello.c is the file with the problem.
  • 4 is the line number, and 28 is how far into that line (the column).
  • error: expected ';' before 'return' is what went wrong, in (almost) plain English.

Notice that the compiler noticed the problem only when it reached return. So if the line it points to looks fine, always check the line right before it too.

Fix the first error first

Sometimes one tiny mistake gives you a whole wall of errors, because the compiler gets confused and everything after the mistake looks wrong to it. So don't panic. Always fix the very first error, compile again, and see what's left. Very often, the rest just disappear.

Errors vs warnings

An error means the compiler couldn't make your program at all. A warning means it did make it, but something looks wrong. Never ignore warnings. A warning today is very often a bug (or even a vulnerability) tomorrow.

Errors you will see a lot

The compiler saysWhat it usually means
expected ';' before ...You forgot a semicolon, usually at the end of the line before.
implicit declaration of function 'Printf'C has never heard of that function. Check the spelling (C is case-sensitive!), or you're missing an #include.
expected declaration or statement at end of inputYou forgot a closing } somewhere.
'x' undeclaredYou used a variable that doesn't exist. A typo, or you forgot to create it.

When it compiles but does the wrong thing

The worst bugs are the ones where there's no error at all. The program runs, it just does the wrong thing. For these, the simplest trick is also the most used one: add some printfs to see what's actually happening inside your program, step by step. Print the values you think you have, and compare them with what you expected. The moment they don't match, you found your bug. Once you are done, remove those extra printfs.

And if you're still stuck, try explaining your code, line by line, out loud, to anybody, even a rubber duck. It sounds silly, but very often you will find the bug halfway through explaining it. Programmers actually call this rubber duck debugging!
